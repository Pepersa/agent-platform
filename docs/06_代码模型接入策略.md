## 0. 摘要（TL;DR）

1. **当前机器装不下第三个常驻 GPU 模型，这是物理事实，不是配置问题。** gpt-oss-20b 在 32K 上下文下实测占用 **15616 MiB**（本机 `nvidia-smi` 实测），总显存 16303 MiB，**仅剩 292 MiB**。Qwen2.5-Coder-14B-Q4_K_M 权重 8.99 GB + KV/overhead ≈ 11–13 GB，**无物理空间**。
2. **推荐方案：E（混合）** —— gpt-oss-20b 常驻 GPU 做主力推理；代码模型按需 CPU 推理（方案 B 形态），仅处理「纯代码生成/编辑」子任务；同时**保留方案 D（部分 offload）作为升级路径**（用 `--n-cpu-moe`，不是 `--n-gpu-layers`）。
3. **但必须先承认一个事实**：本机 CPU 跑 14B Q4_K_M **实测 6.14 tok/s 解码速度**（Ryzen 7 9800X3D + 93.66 GB RAM，`deploy/start_servers.ps1` 标准实例，curl 流式测量，§2.5），交互式代码生成**不可用**（生成 200 行模块要 ~4.3 分钟）。因此代码模型上 GPU 是**必须的**，只是**不能常驻**。真正的解法是**顺序换入（方案 C）+ 按需冷启动**，而非「三模型同时在」。
4. **本次已落地的代码改动**（不需要下载任何模型）：新增 `code` 路由、`capabilities` 能力标签机制、**降级保护**（代码任务绝不静默降级到非代码模型）、`scripts/verify_model_routing.py`（83 项断言全过）。
5. **v1.1 实测新发现（三条，都与原判断不同）**：
   - **GPU 实际有 ~200 tok/s**（不是原先以为的 22 tok/s）—— 原数字来自一个**配置错误的老实例**（`-c 8192` 且未开 flash-attn），标准实例快 **9 倍**。CPU/GPU 差距是 **~33 倍**（200 vs 6.14）；
   - **原以为 `reasoning_effort` 有 6 倍加速杠杆 —— 实测不成立**。干净实例上 high/low 交替 3 轮，各档位区间完全重叠（173–206 tok/s），无统计差异。真正影响耗时的是**推理 token 占比**。另：`chat_template_kwargs.reasoning_effort` 是 llama.cpp 正确传参形式 ✅，顶层 `reasoning_effort` 字段 llama.cpp **不识别** ⚠️；
   - **⚠️ 定位并修复了一个真实的生产故障**：API 进程里的 bge-m3 / bge-reranker 因 FlagEmbedding 默认选 CUDA，**抢占 +5.6 GB 显存**，与常驻的 gpt-oss-20b 合计 22.3 GB > 16.3 GB → OOM → **两个 llama-server 一起崩溃**（实测复现 2 次）。已强制 BGE 走 CPU，修复后 `/kb/search` 仅 **+119 MiB**，并发压力测试全过（§2.5.2 发现③、§7.2.1）。
6. **诚实结论**：在 16 GB 单卡 + 「不能起第三个 Python GPU 进程」的硬约束下，**没有免费的午餐**。要么接受 CPU 代码模型 ~6 tok/s 的延迟（适合后台批处理），要么接受模型换入的 20–40 秒冷启动，要么加卡（24 GB 是本场景真正的甜点）。本文给出三者的量化对比与推荐。

1. **16 GB 显存装不下第三个常驻 GPU 模型。** 剩余 292 MiB，任何 ≥1 GB 的模型都进不去。

### 2.4 llama.cpp 部分卸载（`--n-gpu-layers`）的可行性与代价

**结论：dense 模型不要用部分卸载；MoE 模型要用 `--n-cpu-moe` 而不是 `--n-gpu-layers`。**

**为什么 dense 模型的部分卸载很痛**（这是「调和平均数」效应）：

> 32 层模型，GPU 全驻留 60 tok/s，CPU 5 tok/s。放 28 层 GPU + 4 层 CPU：
> ```
> gpu part: 28/32 × (1/60) = 0.0146 s
> cpu part:  4/32 × (1/5)  = 0.0250 s
> total    =  0.0396 s  →  25 tok/s
> ```
> **12% 的层放在 CPU 上，代价是 58% 的速度。**

14B Q4_K_M（40 层）在 RTX 3060 12GB + Ryzen 5800X 上的实测曲线：

| CPU 上的层数（总 40） | tok/s | 相对纯 GPU |
|---|---|---|
| 0（全 GPU） | 38 | 1.0× |
| 4 | 16 | **2.4× 慢** |
| 8 | 9 | **4.2× 慢** |
| 16 | 5 | **7.6× 慢** |
| 40（全 CPU） | 4 | 9.5× 慢 |

**「差一点放不下」是本地推理最难受的位置** —— 官方建议：**与其部分卸载，不如再降一档量化**（Q4_K_M → Q4_K_S，8.99 → 8.57 GB）让它全驻留。

**MoE 模型的正确做法**（gpt-oss-20b 和 Qwen3-Coder-30B 都是 MoE）：
- 专家权重占大量显存，但**每 token 只激活少数专家** → 把专家放 RAM，**带宽账单很小**。
- llama.cpp 提供 `--n-cpu-moe N`（前 N 层的专家放 CPU）与 `--cpu-moe`（全部专家放 CPU）。
- 16 GB 卡的推荐配置（社区实测）：
  ```bash
  llama-server -m Qwen3-Coder-30B-A3B-Instruct-Q5_K_XL.gguf \
    -ngl 99 --n-cpu-moe 16 -fa -ctk q8_0 -ctv q8_0 -c 32768
  ```
- RX 7900 XT 20GB 上 gpt-oss-20b 的实测曲线（全驻留 94 tok/s → 4 层专家下放 60 → 8 层 38 → 16 层 25–27 → 全下放 20）。

### 2.5 CPU 推理（`-ngl 0`）跑 14B 代码模型的真实 tok/s —— **本机已实测**

**结论（本机实测）：GPU gpt-oss-20b = ~200 tok/s；CPU qwen2.5-14b (Q4_K_M) = 6.14 tok/s。两者相差 ~33 倍。**

#### 2.5.1 本机实测数据（v1.1 最终版，2026-11-23）

**测量环境**：`deploy/start_servers.ps1` 启动的标准实例（`-c 32768`、`--cache-type-k/v q8_0`、`--flash-attn on`、`-ngl 99` / `-ngl 0`）。

| 场景 | 模型 / 量化 | 端点 | 运行方式 | output tok | TTFB | **解码 tok/s** |
|---|---|---|---|---|---|---|
| **CPU 基线** | `qwen2.5-14b`<br>Q4_K_M | `:8081` | **CPU**（`n_threads=8`） | 400 | 0.00 s | **6.14 tok/s** |
| **GPU 基线** | `gpt-oss-20b`<br>MXFP4 MoE | `:8080` | GPU 全 offload | 393–399 | 0.00–0.03 s | **182.8 – 210.1 tok/s** |

> **服务器端独立佐证**（`data/logs/*.log.err` 的 `print_timing`，与客户端测量互为印证）：
> ```
> GPU: eval time =  789.61 ms / 148 tokens (5.37 ms per token, 186.17 tokens per second)
> GPU: eval time =  947.23 ms / 200 tokens (4.76 ms per token, 210.09 tokens per second)
> CPU: eval time = 64355.29 ms / 400 tokens (161.29 ms per token,  6.20 tokens per second)
> ```

> **测量方法（重要，别用错）**：用 `curl -N` 流式 + `-w "%{time_starttransfer} %{time_total}"` 把 **TTFB（首 token 延迟）** 与 **解码速度** 分开算。
> ```powershell
> $obj = @{ model="qpt-oss-20b"; messages=@(@{role="user";content="<prompt>"}); max_tokens=400; stream=$true }
> $obj | ConvertTo-Json -Depth 6 -Compress | Out-File tmp.json -Encoding utf8 -NoNewline
> curl.exe -s -N -X POST http://127.0.0.1:8080/v1/chat/completions -H "Content-Type: application/json" --data-binary "@tmp.json" -w "`nTTFB=%{time_starttransfer} TOTAL=%{time_total}`n"
> ```
> 解码 tok/s = `数据行数 / (TOTAL − TTFB)`

> ⚠️ **踩过的三个坑（v1.1 全部踩了一遍，数字被污染了 9 倍）**：
> 1. **实例配置不对**：最初跑的是一个 **`n_ctx_slot = 8192`** 的旧实例，且没带 `--flash-attn`。用 `deploy/start_servers.ps1` 起的标准实例（`-c 32768` + flash-attn）速度是它的 **9 倍**。
> 2. **API 进程抢显存**：bge-m3 / bge-reranker 因 FlagEmbedding 默认选 CUDA，**+5.6 GB**，与 gpt-oss 合计超卡 → llama-server OOM 崩溃。**已修复**（见 §2.5.2 发现③）。
> 3. **并发污染**：同机另一个 CPU 基准任务抢占内存带宽，会把 GPU 基准从 200 打到 5.58 tok/s。**基准必须串行、独占、重复至少 3 次取中位数。**
> 👉 **结论：任何 tok/s 数字都必须标注「实例配置 + 是否并发 + 测量方法」，否则不可复现、不可比较。**

#### 2.5.2 三个重要发现

**① CPU 与 GPU 差 ~33 倍，比原先估计的「4–20 倍」更悬殊。**
实测：GPU **~200 tok/s** vs CPU **6.14 tok/s**。6.14 tok/s 的实际含义：
- 生成一个 50 行的函数（~400 tok）→ **~65 秒**
- 生成一个 200 行的模块（~1600 tok）→ **~4.3 分钟**

> **CPU 代码模型只适合「后台批处理」**（异步生成测试脚手架、批量补全、离线评测），**不适合交互式 Agent 主循环**。
> 且 CPU 推理**不占任何显存**，与 `:8080` 的 gpt-oss **零冲突并行** —— 这是方案 E 的价值所在。

**② `reasoning_effort` 对速度的影响：实测「无可复现影响」。**（v1.1 初稿曾误判为 6 倍杠杆，已修正）

在**干净实例**上做的交替对照（high/low 交替 3 轮，`chat_template_kwargs` 形式）：

| 配置 | 各次实测解码 tok/s | 结论 |
|---|---|---|
| `chat_template_kwargs` = `high` | 173.58 / 202.90 / 203.09 | — |
| `chat_template_kwargs` = `low` | 198.54 / 199.94 / 199.65 | — |
| 无参数（400 tok） | 202.64 | — |
| `low`（400 tok） | 182.81 | — |
| `high`（400 tok） | 205.54 | — |

👉 **各档位速度区间完全重叠（173–206），无统计差异。**
   - `chat_template_kwargs.reasoning_effort` 是 llama.cpp 侧的正确传参形式（项目 `llm_client.py:421` 用的就是它）✅；
   - 顶层 `reasoning_effort` 字段 llama.cpp **不识别**（OpenAI 兼容层的宽松字段）⚠️；
   - **真正决定速度的是「推理 token 占比」**（reasoning token 全计入 `completion_tokens`），而不是 effort 档位本身。
   👉 **落地建议（理由已修正）**：**按任务类型设**，而不是「用 low 换速度」：
> `agent`/`tool_call`/`ask` → `low`（推理 token 少 → 总耗时长）；
> `plan`/`reasoning` → `medium`；深度调试 → `high`。
> 这是「**减少要生成的 token 数**」，不是「换个参数就变快」。

**③ 发现一个真实故障并已修复：API 进程的 BGE 模型抢显存，把两个 llama-server 一起拖崩。** ⚠️ **这是本次最重要的发现。**

**症状**（实测复现两次）：
- llama-server 日志：`E CUDA error: an illegal memory access was encountered`（`ggml-cuda.cu:833`）→ **两个推理服务全部崩溃**；
- API 日志同步出现：`CUDA error: unknown error`、`Reranker 异常，回退到 RRF 顺序`、`向量通道异常`、`LLM 调用失败 … WinError 10061`（连接被拒）；
- 更糟的一种形态：**服务不崩溃但请求被静默拖死 120 秒**（`Read timed out`），且解码速度从 196 → 47 → 18 → 5.75 t/s 逐级衰减。

**根因（已在源码级确认）**：
```
FlagEmbedding/abc/inference/AbsEmbedder.py:122
    if devices is None:
        if torch.cuda.is_available():
            return [f"cuda:{i}" for i in range(torch.cuda.device_count())]
```
`BGEM3FlagModel` / `FlagReranker` 构造时**没传 `devices`** → FlagEmbedding **自动选 CUDA** → bge-m3 + bge-reranker 加载到显存。

**实测显存账**：
```
API 进程首次调 /kb/search 前 :  1327 MiB
API 进程首次调 /kb/search 后 :  6908 MiB   (+5581 MiB ← BGE 两个模型)
gpt-oss-20b 常驻             : 15437 MiB
─────────────────────────────────────────────────
合计                         : 22344 MiB  >  16303 MiB 总显存  →  OOM
```

**修复（已落地并验证）**：
- `agent_platform/knowledge/embed.py` → 新增 `resolve_flag_devices()`，默认返回 `"cpu"`；
- `embed.py` / `reranker.py` → 构造模型时显式传 `devices=resolve_flag_devices()`；
- `scripts/restart_api.py` → `env.setdefault("BGE_DEVICES", "cpu")`；
- 可用 `BGE_DEVICES=cuda:0` 显式放开（自行承担 OOM 风险），`BGE_DEVICES=auto` 交回 FlagEmbedding 自动探测。

**修复效果实测**：
| 场景 | 修复前 | 修复后 |
|---|---|---|
| `/kb/search` 后显存增量 | **+5581 MiB** | **+119 MiB**（仅 CUDA context） |
| 空闲显存 | 89–460 MiB（危险） | **2635 MiB**（健康） |
| llama-server CUDA 错误 | 复现 2 次 | **0 次** |
| 压力测试（2×KB + 2×LLM 并发） | 服务崩溃 | **全部成功，服务存活** |

> 👉 **这条发现独立印证了本文档的核心结论**：16 GB 单卡的显存预算极其紧张，**不只是「装不下第三个 LLM」，连 API 进程里的辅助模型都会把它挤爆**。
> **任何新增 GPU 占用者（embedding / reranker / OCR / 其他 vLLM 实例）都必须先核算显存，并默认放 CPU。**

  → ⚠️ **本机 9800X3D + 96 GB 正是这条路径的典型配置**（公开值 ~15 tok/s），**值得实测对比** —— 一个 30B-A3B MoE 在 CPU 上可能比 14B dense **快 2.5 倍**且代码能力更强（>70% SWE-bench）。这是**独立的高价值探索方向**（本文档 §6 之外）。
  → ⚠️ 但注意：本机 `:8081` 只用了 **`n_threads = 8`**（日志实测），而 CPU 是 **8 核 16 线程**。**`-t 16` 可能把 6.14 tok/s 再提 20–40%** —— 这是**零成本**的优化，值得试。

#### 2.5.4 对本项目的直接含义

- 现有 `:8081` 跑 Qwen2.5-14B CPU 已经是本平台的**「最快 CPU 路径」**（实测 6.14 tok/s，可再试 `-t 16`）；
- 换成 Qwen2.5-Coder-14B CPU **不会更快**（同为 14B Q4_K_M，预期 ~6 tok/s），只会多一个代码能力；
- **CPU 代码模型适合「后台批处理」，不适合交互式 Agent 主循环**；
- 但如果**代码子任务允许异步**（Agent 提交任务 → 后台生成 → 轮询取回），**6 tok/s 完全可用** —— 这是方案 E 的落地形态；
- ⚠️ **GPU 侧现在有 ~200 tok/s 的余量**（原先以为只有 22 tok/s）。若某天需要「代码模型也上 GPU」，方案 C（顺序换入）的等待成本比原估计更痛 —— 但**质量差距也随之更大**。

### 2.6 官方推荐起点小结

- **Qwen2.5-Coder-14B-Instruct Q4_K_M**：8.99 GB，16 GB 卡 **Q4_K_M @32K 需 ~16.3 GB** —— 本机 16 GB **放不下 @32K**（放得下 @8–16K）。
- **Qwen3-Coder-30B-A3B-Instruct Q5_K_XL + `--n-cpu-moe 16`**：这是社区在 16 GB 卡上跑 coder 的**标准配置**。
- **gpt-oss-20b MXFP4**：OpenAI 原生 MXFP4 权重（**不是**事后量化），所以同尺寸下质量略优于 Q4_K_M。

## 3. 方案对比（A–E）

### 3.1 硬约束下的对比表

| 方案 | 显存 | 速度（代码任务） | 代码质量 | 复杂度 | 切换代价 | 结论 |
|---|---|---|---|---|---|---|
| **A. 单模型多角色**<br>只用 gpt-oss-20b，调高 reasoning_effort | 15.6 GB（不变）<br>✅ 无需改动 | **182–210 tok/s 实测**<br>（TTFB ≈ 0 s） | **中**：HumanEval 73% 但非专用 coder 训练；工具调用 91.1% ✅ | **零**：只改 prompt | 无 | ⭐ **立即可用的基线**，但代码上限受限 |
| **B. CPU 按需换入**<br>`:8081` 换 code 模型跑 CPU | 0（不占显存）<br>✅ 显存不是瓶颈 | **6.14 tok/s 实测** ❌<br>交互式不可用 | 高（专用 coder） | 低：换 GGUF + 改端点 | 冷启 ~10–20 s（CPU 加载快） | ⚠️ **只适合后台批处理**；交互式不可用 |
| **C. 顺序换入**<br>停 gpt-oss → 起 code 模型（GPU） | 独占 16 GB ✅ | **~150–200 tok/s**（同卡实测 gpt-oss 水平，coder 尺寸相近） | **高** | 中：需编排脚本/服务管理 | **冷启 20–40 s**（GGUF 加载 + CUDA init）<br>+ 切回再等 20–40 s | ⭐ **质量最优的可行路径**，代价是切换延迟 |
| **D. 部分 GPU offload**<br>code 模型 `-ngl N` 部分层上 GPU | 混合 | **断崖式下降**：4 层下放即 2.4× 慢 | 高 | 低：只改启动参数 | 无（常驻） | ❌ **dense 模型不推荐**；<br>✅ **MoE 模型用 `--n-cpu-moe`** |
| **E. 混合** ⭐<br>gpt-oss GPU 主力 + code 模型 CPU 处理纯代码子任务 | 15.6 GB + 0 ✅ | 主力 **182–210 tok/s 实测**<br>代码子任务 **6.14 tok/s 实测** | 主力中 / 代码子任务高 | 中：需在图里加「子任务分流」 | 无（并行） | ⭐⭐ **推荐**：**零切换代价**，且不破坏现有链路 |

### 3.2 逐项点评

**A. 单模型多角色** —— 零成本、零风险，但**不是「代码专用模型」**。它解决不了「需要一个真 coder」的需求，只能缓解。**定位：兜底 + 基线。**

**B. CPU 按需换入** —— 关键矛盾：**CPU 14B 实测 6.14 tok/s**（GPU 是 182–210 tok/s，**差 ~33 倍**）。一段 200 行的函数要生成 ~1600 token，需要 **~4.3 分钟**。**不可用于交互式。** 但本项目已有 `:8081` 跑 CPU 14B 的先例（**实测 6.14 tok/s**），说明**这条路的运维成本已被验证过**。

**C. 顺序换入** —— 唯一能拿到「专用 coder + 可接受速度」的路径。代价是：
- 冷启动 20–40 s（GGUF mmap + CUDA context + KV 分配）；
- **切换期间服务不可用**（或至少该路由不可用）；
- 需要一个**编排层**（停旧进程 → 起新进程 → 探活 → 切路由 → 切回）。

**D. 部分 offload** —— 对 dense 模型是「速度陷阱」（§2.4 的调和平均数）。**但对 MoE 模型（Qwen3-Coder-30B-A3B）用 `--n-cpu-moe` 则完全成立** —— 这是本文档给出的**升级路径**：如果将来愿意下 18.6 GB 的 Qwen3-Coder-30B-A3B，可用 `--n-cpu-moe 16` 在 16 GB 卡上以 ~200 tok/s 跑 coder 30B。

**E. 混合（推荐）** —— 逻辑最清晰：
- **主力推理/工具调用/规划** → gpt-oss-20b（GPU，**182–210 tok/s 实测**，91.1% MCP 分）；
- **纯代码生成/编辑子任务** → code 模型（CPU，**6.14 tok/s 实测**，或按 §6 升级到 GPU 换入）；
- **两套进程不冲突**（一个 GPU、一个 CPU），**不需要编排切换**；
- **降级保护**由能力标签机制保证（§4）。

### 3.3 推荐方案

> **推荐 E（混合）+ 预留 C（顺序换入）作为「重代码任务」的高质量档位。**

**具体形态（分三层）**：

```
┌─────────────────────────────────────────────────────────────┐
│  Tier 1  日常 Agent 循环 / 推理 / 工具调用 / 规划            │
│          → gpt-oss-20b  @ :8080  (GPU, -ngl 99)             │
│          → 现状，**零改动**                                 │
├─────────────────────────────────────────────────────────────┤
│  Tier 2  纯代码生成 / 编辑子任务                              │
│          → qwen2.5-coder-14b  @ :8082  (CPU, -ngl 0)        │
│          → 新增（需先下载 8.99 GB），走 code 路由             │
│          → 慢（6.14 tok/s 实测）但**质量高**，适合后台/批量          │
├─────────────────────────────────────────────────────────────┤
│  Tier 3  重代码任务（可选，按需换入）                          │
│          → qwen2.5-coder-14b  @ :8082  (GPU 全 offload)      │
│          → 需停掉 Tier 1 的 gpt-oss，冷启 20–40 s            │
│          → **由运维手动/脚本触发**，不自动切换                │
└─────────────────────────────────────────────────────────────┘
```

**理由**：
1. **不破坏现有链路**：Tier 1 完全不动，`verify_modes.py` 的断言全部保持。
2. **零切换代价起步**：Tier 2 与 Tier 1 并行，随时可用。
3. **质量上限有出口**：Tier 3 只需改一行启动参数（`-ngl 0` → `-ngl 99`）与停/起 gpt-oss。
4. **降级安全**：能力标签保证「代码任务不会掉到非代码模型」（§4）。
5. **诚实**：如果 Tier 2 的 **6.14 tok/s（实测）** 不可接受，**唯一正确的解法是加卡**（24 GB）或接受 Tier 3 的切换延迟 —— 16 GB 单卡 + 常驻双模型的组合在物理上不存在。
   > 补充：实测还发现旧 llama-server 实例出现过 **CUDA illegal memory access**（显存余量仅 89–460 MiB 时触发，§2.5.2 发现③）。**已通过统一使用 `deploy/start_servers.ps1`（`-c 32768` + flash-attn + KV 量化）解决**，重启后空闲显存 1556 MiB、未复现。

## 4. 降级保护机制（本次已落地）

### 4.1 问题

原配置：

```yaml
agent:
  fallback: [gpt-oss-20b, qwen2.5-14b]
tool_call:
  fallback: [gpt-oss-20b, qwen2.5-14b]
```

`qwen2.5-14b` 是 **Qwen2.5-14B-Instruct 通用对话模型**，**不是 Coder 型号**。Agent 模式会调用 `ws_write_file` / `ws_edit_file` 写代码 —— 一旦主模型失败，代码任务落到它身上，产出质量**静默**崩塌：用户看到的是一段「看起来能跑、实则不靠谱」的代码，**没有任何报错提示**。

更隐蔽的是：`app.py` 的 `router_client()` 直接取 `chain_for(task_type)[0]`，**完全绕过了 fallback 链**，所以即使在 `LLMRouter.chat()` 里加了校验，主链路也保护不到。

### 4.2 解决方案：能力标签（Capability Tags）

**三层机制**：

**① 模型声明能力**（`config/routing.yaml` 的 `models:` 段）

```yaml
gpt-oss-20b:
  capabilities: [code, tool_call, reasoning, chinese]

qwen2.5-14b:
  # ⚠️ 刻意不给 code —— 它是通用对话模型，不是 Coder
  capabilities: [tool_call, reasoning, chinese]

qwen2.5-coder-14b:
  capabilities: [code, tool_call, reasoning, chinese]
  installed: false        # 占位：如实告知未安装
```

**② 路由项声明所需能力**（`routes:` 段的 `requires:`）

```yaml
code:
  fallback: [qwen2.5-coder-14b, gpt-oss-20b]
  requires: [code]

agent:
  fallback: [gpt-oss-20b]
  requires: [code, tool_call]      # ← 移除了 qwen2.5-14b

tool_call:
  fallback: [gpt-oss-20b]
  requires: [tool_call]            # ← 移除了 qwen2.5-14b
```

**③ 路由器执行校验**（`agent_platform/core/llm_client.py`）

- `LLMRouter.filtered_chain_for(task_type)`：剔除链中缺能力的模型；
- `LLMRouter.route(task_type)`：取**第一个合格**模型；一个都没有 → 抛 `RoutingCapabilityError`；
- `LLMRouter.chat(task_type, ...)`：沿链降级时**跳过**缺能力的模型；
- `LLMRouter.validate_routes()`：静态自检，返回违规降级列表；
- `LLMRouter.routing_report()`：导出完整报告（供 `/health` 与验证脚本）。

**未声明 `requires:` 的路由项**（`default` / `chinese` / `eval` / `summarize`）**无能力约束**，链原样保留 —— 这些任务不写代码，不需要保护。

### 4.3 行为对照

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 代码任务，主模型正常 | 走主模型 | ✅ 走主模型（不变） |
| 代码任务，主模型挂了，链里有 `qwen2.5-14b` | ⚠️ **静默降级**到通用对话模型，代码质量崩 | ✅ 跳过 `qwen2.5-14b`；若无合格模型 → **显式报错** `RoutingCapabilityError` |
| 中文/摘要任务，主模型挂了 | 降级到 `qwen2.5-14b` | ✅ 不变（该路由无能力约束） |
| 用户注册了一个别名模型（未知） | 出现在 `default` 链里 | ✅ 仍出现在 `default`；但**不会**被用作代码类备选（无任何能力标签） |

### 4.4 新增异常类型

```python
class RoutingCapabilityError(RuntimeError):
    """fallback 链里没有具备所需能力的模型（**显式失败**，不静默降级）。"""
```

错误信息会明确告诉用户**下一步该做什么**（装哪个模型 / 看哪份文档），而不是一个模糊的 502。

```python
# LLMRouter —— 核心校验方法
def filtered_chain_for(self, task_type: str) -> List[str]:
    """返回**经过能力校验**的 fallback 链（剔除缺能力的模型）。"""
    chain = self.chain_for(task_type)
    required = self.required_capabilities(task_type)
    if not required:
        return chain
    return [m for m in chain
            if all(self.has_capability(m, cap) for cap in required)]

def validate_routes(self) -> List[str]:
    """自检：返回所有「违规降级」的问题描述列表（空列表 = 全部合法）。"""
    problems: List[str] = []
    for task_type in sorted(self.routes):
        required = self.required_capabilities(task_type)
        if not required:
            continue
        for model_name in self.chain_for(task_type):
            missing = [c for c in required if not self.has_capability(model_name, c)]
            if missing:
                problems.append(
                    f"路由 '{task_type}' 的降级链包含模型 '{model_name}'，"
                    f"它缺少能力 {missing}（要求 {required}）")
    return problems
```

```python
# app.py —— 修掉绕过能力校验的漏洞
def router_client(self, task_type: str = "agent") -> LLMClient:
    """按路由项取 LLM 客户端（复用 config/routing.yaml 的 routes）。

    ⚠️ 历史实现直接取 chain_for(task_type)[0]，跳过了能力校验，
    会让代码类任务静默落到不具备代码能力的模型上 —— 现已修正。
    """
    if self.router is None:
        self.llm()
    assert self.router is not None
    return self.router.route(task_type)
```

```powershell

  -m "E:\model\models\bartowski\Qwen2.5-Coder-14B-Instruct-GGUF\Qwen2.5-Coder-14B-Instruct-Q4_K_M.gguf" `

**参数说明**：
- `-ngl 0` → **纯 CPU**（不占显存，与 :8080 的 gpt-oss 并行共存）；
- `-t 16` → 16 线程（本机 16 逻辑线程；llama.cpp 建议用**物理核心数**，实测 8 线程常快于 32 线程，**装完请用 `llama-bench` 实测确定**）；
- `--cache-type-k/v q8_0` → **KV cache 量化**（显存减半）。本项目现有两个端点都已启用，**不要省**；
- `--flash-attn on` → **必须**。v1.1 实测：老实例没开 flash-attn 且 `-c` 只有 8192 时，**解码速度只有标准实例的 1/9**（22 vs 200 tok/s），且出现过 **CUDA illegal memory access**；
- `--jinja` → **必须**，否则 `tools` 参数被忽略、没有 function calling；
- `--alias` → 让 `/v1/models` 返回 `qwen2.5-coder-14b`，与 routing.yaml 里的 `model:` 对齐；
- `-c 32768` → 与其他两个端点一致（保持 `deploy/start_servers.ps1` 的口径）。

## 9. 诚实说明与待决策问题

### 9.1 「当前机器为什么装不下」的诚实说明

```
GPU 总显存              16303 MiB
gpt-oss-20b 已占用      15616 MiB   （实测 nvidia-smi）
─────────────────────────────────────
剩余                     292 MiB   ← 装不下任何 ≥1 GB 的模型
```

**为什么不能「挤一挤」**：
- Qwen2.5-Coder-14B Q4_K_M @32K 的**纯模型+KV**估算 **16.3 GB**，@16K **13.1 GB**，@8K **11.4 GB**；
- 即使降到 @8K（11.4 GB），也**远超**剩余的 292 MiB；
- gpt-oss-20b 占的 15.6 GB **不能压缩** —— 它是 MXFP4 原生权重（OpenAI 只发布 MXFP4，没有 Q4_K_M 版本），11.28 GB 权重 + 24 层 MoE + 32K 上下文的 KV + CUDA context 是硬开销；
- 降低 gpt-oss 的上下文能省 KV，但省不出 10 GB。

**为什么不能「第三个 Python 进程」**：
- 新进程 `import torch` 会**挂起 >150 秒**（CUDA context 与 llama.cpp 争用），这是已实测确认的；
- bge-m3 已在 API 进程内用 FlagEmbedding 跑 CPU，**GPU 放不下也不需要放**。

**结论**：16 GB 单卡 + 「gpt-oss 全量常驻」+「不能起第二个 GPU 进程」这三个条件同时成立时，**第三个常驻 GPU 模型在物理上不存在**。任何声称「可以同时跑三个」的方案要么违反其中一条，要么依赖本文档未验证的技术（如自定义 CUDA 多进程共享）。
