# 03 · GPU 显存与模型规模选型计算表

> 适用对象：半导体测试设备公司（数据不出内网、私有化部署场景）
> 用途：GPU 采购/借用前的技术选型与容量规划
> 文档版本：v1.0 ｜ 编制日期：2026-11
> **免责声明：文中所有算力、显存、吞吐、价格均为公开资料 + 工程经验推导的「估算/参考值」，实际以供应商报价、实测 benchmark 为准。**

---

## 0. 摘要

1. **显存不是买卡的理由，显存带宽和互联才是。** 大模型推理的 decode 阶段是**显存带宽受限（memory-bound）**，不是算力受限。因此选卡第一优先级是「显存容量 > 显存带宽 > 卡间互联带宽 > 峰值算力」。消费级 4090/5090 带宽极高（1.0 / 1.79 TB/s）但显存小、无 NVLink，适合单卡小模型，不适合张量并行。
2. **7B / 14B 级模型已经够用。** 内部 50–200 人规模的知识问答、文档分析、缺陷描述生成，Qwen3-8B/14B（FP8 或 AWQ-INT4）在单卡 L20/L40S/5090 上即可满足。**32B 用于复杂推理与代码，MoE-30B-A3B 是「性价比甜点」**（总参 30B 但每 token 只激活 3B，显存要全存、速度按 3B 算）。
3. **单机多卡优于多机。** 张量并行（TP）在 NVLink/PCIe 域内才划算。跨机张量并行会把 100GB/s 的 PCIe 通道当高速公路用，吞吐可能掉 2–3 倍。方案 B 强烈推荐「单机 4 卡」而非「2 机 × 2 卡」。
4. **单卡 vs 多卡的性价比拐点**大致在显存 24GB 附近：≤24GB 显存时，多卡 Z-axis 切分的通信开销（all-reduce）吃掉大部分收益；≥48GB 且走 NVLink 时，多卡几乎线性增益。
5. **数据敏感场景自建是刚需，不是经济选择。** 本测算显示：50 人规模年 API 费用仅约 3,000 元人民币，而自建年 TCO 在 9–12 万元，**自建在经济上永远不划算**；自建的理由是数据合规、离线可控、无外网依赖、模型可私有微调。**盈亏平衡点在每天约 4.5 万请求 / 6,500 万 token 以上**（对应 1,000+ 人规模或高频自动化场景）。
6. **强烈建议先「借用已有工作站 GPU」做 POC。** 公司测试机/工作站上的 RTX 4090 / RTX A6000 几乎免费可用（电费一年约 3,000–4,000 元），足够跑通 7B/14B 的评测基线，为后续 100 万级采购提供真实吞吐数据。

- Ada（4090/L20/L40S）支持 FP4（稀疏），Blackwell（5090）支持 FP4 稠密，Hopper（H100/H200）支持 FP4 稀疏 —— 但**目前开源生态中 FP4 权重的成熟度远低于 FP8**，生产环境建议 FP8 或 AWQ-INT4。

### 1.2 单卡 vs 多卡的性价比拐点

多卡收益来自两处：① 容量叠加（TP 切权重）；② 吞吐叠加（数据并行 / 多实例）。

| 卡间互联 | 单向有效带宽 | TP=2 / TP=4 的通信占比影响 |
|---|---|---|
| PCIe 4.0 x16 | ~32 GB/s（双向 64） | **通信瓶颈明显**，TP>2 时 decode 吞吐常掉 30–60% |
| PCIe 5.0 x16 | ~64 GB/s（双向 128） | TP=2 可接受，TP=4 仍偏慢 |
| NVLink 3.0（L40S×2 板卡互联） | ~100–200 GB/s | 基本线性 |
| NVLink 3.0（H100/A100 SXM） | 450 GB/s | 几乎线性增益 |
| NVLink 4.0（H200/GB200） | 900 GB/s | 最优 |

**拐点结论（估算）**
- **单卡显存 ≤ 24 GB（如 4090）**：多卡 TP 收益被 all-reduce 通信吃掉。**优先用「多实例并行（MPS / 多进程）」而不是张量并行**。例如 4×4090 跑 4 份 8B 模型，整体吞吐远高于 4×4090 TP 跑 1 份 32B。
- **单卡显存 48–80 GB（L20/L40S/A100/H100）**：TP=2、TP=4 均可获得 70–95% 的线性增益（取决于互联）。
- **单卡显存 ≥ 141 GB（H200）**：单机 2–4 卡 TP 几乎线性，是 MoE 大模型的甜点区。
- **量化拐点经验公式**：`有效吞吐增益 ≈ 卡数 × 0.75 ~ 0.95`（NVLink）；`≈ 卡数 × 0.4 ~ 0.7`（纯 PCIe，TP 模式）。

### 1.3 消费级卡（4090 / 5090）做推理的可行性与风险

**可行性（结论：可以做，但要限定用途）**
- 4090（24G）：AWQ-INT4 可放 7B/14B/30B-A3B；BF16 只能放 8B 以内 + 小 KV。
- 5090（32G）：FP8 可放 14B/32B(短上下文)；AWQ-INT4 可放 32B / 30B-A3B / 72B-AWQ。
- 4090/5090 的显存带宽（1.0 / 1.79 TB/s）**高于 L20/A6000**，所以**单请求 decode 延迟往往比 L20 更低**，这是它们的核心价值。

**风险清单**
1. **无 NVLink**：只能走 PCIe，TP 效率低；多卡应做「数据并行多实例」而非 TP。
2. **ECC 缺失**：4090/5090 无 ECC 显存，长时间大模型推理有 **Xid/显存位翻转**风险，导致静默数据错误或进程崩溃。生产环境需配 `nvidia-smi --query-gpu` ECC 状态监控（消费卡不支持）。
3. **散热与机箱**：4090 TDP 450W、5090 TDP 575W 且体积巨大（5090 超过 2 槽、需 600W+ 电源）。**普通办公机箱/工控机往往带不动**（风道与供电）。
4. **机房条件**：多卡密集部署时每卡 500W+ 发热，需要专用机柜（冷板/空调），普通隔断机柜温度会飙升，导致降频。
5. **电力与供电**：单台 4 卡工作站峰值约 2.2–2.6 kW，需要独立 PDU/UPS，不能与办公负载混接。
6. **驱动与授权合规**：需确认显卡是否为「正式版」（禁运型号的变体/魔改卡在部分地区有法律风险）；商用软件许可（vLLM/TensorRT-LLM 本身免费，但商业 LLM 权重的 License 需逐一核对是否允许商用）；Windows 下驱动栈与 Linux 生产环境的差异需额外验证。
7. **无 vGPU / 不支持 SR-IOV 虚拟化**（部分消费卡驱动限制），多租户切分要靠 MIG —— **MIG 仅支持 A100/H100/H200 等数据中心卡，4090/5090 没有 MIG**，无法做硬件级隔离，只能靠进程隔离。

## 2. 显存计算模型（核心公式）

### 2.1 权重显存

```
显存权重(GB) = 参数量(十亿) × 每参数字节数(B) / 1024^3
```

| 精度 | 每参数字节数 | 备注 |
|---|---|---|
| FP32 | 4 | 训练/部分 Embedding |
| BF16 / FP16 | 2 | 推理默认，Blackwell/Ada 支持良好 |
| FP8 (E4M3 / E5M2) | 1 | Hopper/Blackwell 原生，Ada 可模拟但收益有限 |
| INT8 (SmoothQuant/W8A8) | 1 | Ampere 起支持 |
| **FP4 (NVFP4/MXFP4)** | 0.5 | Blackwell 为主，生态尚新 |
| **AWQ 4bit** | **≈0.55** | 含 group scale/zero-point 开销（group=128 时约 +12~15%） |
| **GPTQ 4bit** | **≈0.50** | 含 scale/zero（group=128 时约 +5~8%） |

> 经验值：**INT4 量化后权重体积 ≈ 原 BF16 的 27% ~ 30%**，即压缩比约 3.4×。

### 2.2 KV Cache 显存

```
KV(GB) = 2 × layers × kv_heads × head_dim × seq_len × batch × bytes_per_elem / 1024^3
```
- `2` = K 和 V 各一份
- `bytes_per_elem`：BF16/FP16 = 2；FP8 KV = 1（vLLM 支持 `--kv-cache-dtype fp8`）
- `kv_heads`：GQA 模型为「KV 头数」，MHA 模型 = `q_heads`

**GQA / MQA 缩减倍数**
```
缩减倍数 = q_heads / kv_heads
```
- **MHA**（kv_heads = q_heads）：基准，无缩减。
- **MQA**（kv_heads = 1）：如 Falcon-7B，缩减 32×（7B）/ 64×（70B），KV 极小。
- **GQA**（主流）：Llama-3-8B (32/8 → 4×)、Qwen3-8B (32/8 → 4×)、Qwen3-32B (64/8 → 8×)、DeepSeek-R1-Distill-Qwen-7B (28/4 → 7×)。
- **对照**：若 32B 模型用 MHA（64 KV 头），KV 是 Qwen3-32B（GQA 8 头）的 **8 倍**。

**MLA（Multi-head Latent Attention，DeepSeek 系）**
- 把每个 token 的 KV 压缩为低秩潜在向量：`kv_lora_rank + qk_rope_head_dim`，典型 = 512 + 64 = **576 维/层/token**（不再按头展开）。
- 对比同样 64 头 × 128 维的 GQA：MLA 的 `576` vs GQA 的 `8×128 = 1024` 维 → **单层单 token 缩减约 1.8×**；再叠加 DeepSeek-V3 的 61 层 vs Qwen3-32B 的 64 层，总体差距约 **1.9×**。
- 再加上 MLA 的 **吸收算子（absorb）**优化，可让 decode 阶段几乎不额外读 K/V → **延迟显著下降**。

**手算 KV 速查（BF16，batch=1）**

| 模型 | layers | kv_heads | head_dim | KV@32k (GB) |
|---|---|---|---|---|
| Qwen3-4B / 8B | 36 | 8 | 128 | 4.83 |
| Qwen3-14B | 40 | 8 | 128 | 5.37 |
| Qwen3-32B | 64 | 8 | 128 | 8.59 |
| Qwen3-30B-A3B | 48 | 4 | 128 | 3.22 |
| DeepSeek-V3 (MLA) | 61 | — | 576/层 | 2.30 |
| R1-Distill-Qwen-7B | 28 | 4 | 128 | 1.88 |
| R1-Distill-Qwen-14B | 48 | 8 | 128 | 5.37 |
| R1-Distill-Qwen-32B | 64 | 8 | 128 | 8.59 |
| GLM-4-9B | 40 | 2 | 128 | 1.34 |
| Qwen2.5-VL-72B | 80 | 8 | 128 | 10.74 |

### 2.3 激活值 / 临时缓冲

```
激活(GB) ≈ batch × seq_len × hidden × k × bytes / 1024^3,  k ≈ 2 ~ 4
```
- **Prefill 阶段**是激活峰值所在：形状 `batch × seq_len × hidden × hidden × k`，随 seq_len 线性增长。
- **Decode 阶段**激活极小（`batch × 1 × hidden`），几乎可忽略。
- 所以：**长文档分析要特别关注 prefill 峰值激活**，短 KV 的模型反而可能先被激活显存卡死。

### 2.4 其他开销

| 项目 | 典型占用 | 说明 |
|---|---|---|
| CUDA Graph 捕获 | 0.5–2 GB | 固定 shape 捕获，换 batch 需重捕获 |
| 显存碎片预留 | 总显存的 3–8% | PyTorch caching allocator 的 reserved-but-unused |
| 框架开销（vLLM 等） | **+10–15%** | NCCL、CUDA context、算子 workspace、采样 buffer |
| NCCL 通信缓冲 | 0.5–1 GB / 卡 | TP 通信 |
| 多模态额外 | +2–6 GB | ViT 编码器 + 图像 token 缓存 |

### 2.5 「安全水位」建议

```
可分配显存 = 总显存 × 0.85 ~ 0.90   （剩余 10~15% 给框架/碎片/突发）
```
- **vLLM `--gpu-memory-utilization 0.90`** 是上限值（含 KV 池），启动时它会把 (总显存×util − 权重 − 激活) 全部划给 KV Cache 池；**如果权重本身就占了 90%，KV 池为 0，启动即失败**。
- **经验公式（推理选卡）**：
```
所需总显存 ≈ [ 权重(GB) + KV@目标并发(GB) + 激活(2~4GB) + 框架(10~15%权重) ] / 0.9
```
- **训练选卡**：额外乘以 1.15–1.3 的碎片与通信缓冲系数。

> - **显存按「全部专家参数」计算**（所有专家都要驻留在显存里，随时可能被路由激活）。
> - **计算量（吞吐）按「激活参数量」计算**（每个 token 只走通被选中的 top-k 专家）。
> - 因此 MoE 的显存/算力比极低：Qwen3-30B-A3B 显存 ≈ 30B 模型，但速度 ≈ 3B 模型。

### 3.2 选型速查

- **选 8B 级**：4090 就够；生产用 L20（散热/ECC/可采购）。
- **选 14B 级**：32G 卡（5090/L20-48G 量化后 / A100-40G FP8）；生产推荐 L20/L40S。
- **选 32B 级**：单卡需 FP8 + 48G，或 24G 卡用 AWQ-INT4（17.8GB 权重 + KV 3.4GB(FP8) ≈ 21GB，可塞 5090/4090 略紧）。
- **选 30B-A3B MoE**：**48G 单卡 FP8 = 性价比最优解**（显存同 32B Dense，速度快 2–3 倍）。
- **选 DeepSeek-V3**：只有 H200 级别集群 + FP8 才能落地，属"旗舰"选项；如仅需同等能力，优先评估开源 32B 级 MoE 模型。
- **Embedding / Reranker**：显存占用 < 2GB，可与主 LLM **同卡共存**（在 L20 的剩余 40GB 里塞 bge-m3 + reranker + 向量库索引），**但强烈建议用 MIG 或独立小卡隔离**，避免互相抢显存。

### 4.2 估算过程（逐步）

#### B1：50 人 Agent 助手
```
日请求数        = 50 人 × 30 次/天 = 1,500 次/天
平均输入 token  = 1,200 (系统提示 200 + 检索片段 800 + 对话 200)   ← 估算
平均输出 token  = 400
日输出 token    = 1,500 × 400 = 600,000 tok
日输入 token    = 1,500 × 1,200 = 1,800,000 tok

【prefill】1.8M tok ÷ 6,000 tok/s (L20, 8B BF16 预填充速率估) ≈ 300 s ≈ 0.08 h
【decode】600k tok ÷ 40 tok/s (有效速率估, 含并发摊薄) ≈ 15,000 s ≈ 4.17 h
合计 ≈ 4.25 GPU-h/天 → 负载率 ≈ 4.25/24 ≈ 18%
```
→ **1 张 L20 即可，剩 80% 余量用于峰值并发与长文任务。** 若同时挂载 bge-m3/reranker，同卡仍有余量。

#### B2：200 人规模
```
日请求数 = 200 × 30 = 6,000 次/天
日输出 token = 2,400,000 tok；日输入 token = 7,200,000 tok
decode ≈ 2.4M ÷ 40 = 60,000 s = 16.7 GPU-h
prefill ≈ 7.2M ÷ 6,000 = 1,200 s = 0.33 GPU-h
合计 ≈ 17 GPU-h/天 → 单卡负载率 71%（可接受但峰值风险）
```
→ **推荐 2× L20**：一张跑 8B/14B 主力，一张跑 32B/MoE 与长文任务（KV 池隔离），并留出高峰弹性。若选 Qwen3-30B-A3B（激活 3.3B，decode 快 2–3 倍），单卡负载率可降到 ~30%。

#### B3：100k 超长文档
```
Qwen3-32B, FP8 权重 = 32.8 GB
KV@100k, BF16 = 8.59 GB × (100/32) = 26.8 GB
KV@100k, FP8  = 13.4 GB
prefill 激活峰值 ≈ 1 × 100,000 × 5120 × 3 ≈ 1.46 GB (bf16, 近似)
框架开销 ≈ 10~15% × 32.8 ≈ 4.0 GB

方案甲 (FP8 权重 + FP8 KV): 32.8 + 13.4 + 1.5 + 4.0 ≈ 51.7 GB → 超 48G → 需 A100-80G 或 2×5090
方案乙 (AWQ-4 权重):        17.8 + 13.4 + 1.5 + 2.5 ≈ 35.2 GB → 单卡 L40S/L20 可行
```
→ **推荐：单卡 A100-80G + FP8 KV（余量充足，可再挂小模型）；或 2× 5090 跑 AWQ-INT4（权重分片，各 8.9GB，KV 也在其中）。**
**prefill 吞吐**：32B 在 4090 上约 4,000 tok/s ⇒ 100k 需 ~25 s 首字延迟。**必须开启 Chunked Prefill + Prefix Caching**，否则长 prompt 会阻塞整个 batch（队头阻塞）。

#### B4：多模态 wafer map 批量推理
```
单张 wafer map (2048×2048) 切成 patch → 约 1,500–4,000 视觉 token（取决于 max_pixels）
内部需求：假设 2,000 张/天，平均 2,500 视觉 token + 200 文本 token
日输入 token ≈ 2,000 × 2,700 ≈ 5.4M
LLM prefill 耗时 ≈ 5.4M ÷ 5,000 ≈ 1,080 s
ViT 编码耗时 ≈ 2,000 图 ÷ ~12 img/s ≈ 167 s（估算）
合计 ≈ 0.35 GPU-h/天 → 非常轻
```
→ **瓶颈不在 LLM，而在视觉编码器吞吐与图片读取/预处理**。建议：
- 降低 `max_pixels`（2048×2048 → 1024×1024 可省 4× 视觉 token，缺陷分类精度需实测验证）；
- 使用 **vLLM 离线批量模式**（`LLM.generate` 而非 OpenAI server），避免 HTTP 开销；
- ViT 与 LLM 分卡部署可避免抢占（L20 显存充裕，同卡即可）。

#### 瓶颈判断（prefill vs decode）
```
prefill 时间 ≈ input_tokens ÷ prefill_rate   (prefill_rate 高，30k–80k tok/s on H100, 3k–10k on L20)
decode  时间 ≈ output_tokens ÷ decode_rate     (decode_rate 低，20–200 tok/s)

经验判据：output/input 比 < 1/10  → prefill 主导（RAG、长文档、批量离线）
           output/input 比 > 1/3   → decode 主导（Agent 循环、对话式）
```
- **Agent 助手**：decode 主导 → 优化方向是 **Prefix Caching + 连续批处理 + speculative decoding**。
- **长文档 / RAG 批量**：prefill 主导 → 优化方向是 **Chunked Prefill + FP8 KV + 增大 batch**。

## 5. 推理框架选型与调优清单

### 5.1 框架对比

| 框架 | 吞吐 | 并发能力 | 核心特性 | 易用性 | 部署难度 | 适用场景 |
|---|---|---|---|---|---|---|
| **vLLM** | 高（GPU 满载 2–4× 朴素 HF） | 优秀（PagedAttention + Continuous Batching） | PagedAttention、Prefix Caching、Chunked Prefill、多种量化（AWQ/GPTQ/FP8/FP4）、多模态 | 高 | 中 | **通用首选**，生产推理主力 |
| **SGLang** | 很高 | 优秀 | RadixAttention（比 vLLM Prefix Cache 更强的前缀复用）、结构化输出、投机解码原生、Agent 场景优化 | 中 | 中 | Agent 工作流、多轮复用前缀、复杂结构化生成 |
| **TensorRT-LLM** | 最高（编译优化） | 优秀 | 引擎编译、inflight batching、FP8、插件生态 | 低（需写编译流程） | **高** | 固定模型 + 极高 QPS、延迟要求极严 |
| **llama.cpp** | 中（CPU/GPU 混合） | 低–中 | GGUF 量化（Q4_K_M）、CPU offload、极简 | **很高** | 低 | 边缘/单机、离线批处理、小模型、无 GPU 环境 |
| **Ollama** | 中 | 低–中 | llama.cpp 的极简封装 + API | **很高** | 极低 | 开发者本地试用、快速验证，**不建议做生产服务** |
| **HF Transformers** | 低（无优化调度） | 低 | 生态最全、调试方便 | 高 | 低 | 基准测试、教学、特殊算子 |

**推荐组合**：生产推理 → **vLLM**（生态最成熟、量化支持最全、文档最全）；Agent 前缀复用重的场景 → **SGLang**；极致性能 → **TensorRT-LLM**；POC/借用机器 → **llama.cpp / Ollama**（4090 上 GGUF Q4_K_M 跑 32B 非常快）。

### 5.2 关键参数与最佳实践

| 参数 | 作用 | 建议值 |
|---|---|---|
| `--gpu-memory-utilization` | 显存利用率上限（vLLM 会把剩余全部分给 KV 池） | **0.88 ~ 0.92**（留 8~12% 给碎片/突发）；单卡独占可到 0.93 |
| `--max-model-len` | 最大上下文长度，决定 KV 池分配上限 | **按业务实际设，不要设满**（设 32k 而非 128k，KV 池可多支撑 4× 并发） |
| `--max-num-seqs` | 最大并发序列数 | 32–256；GPU 显存越小越要调小，否则调度抖动 |
| `--max-num-batched-tokens` | 单批 token 数 | 默认 8192/2048；**长文场景调到 16384–32768**，并配合 chunked prefill |
| `--enable-chunked-prefill` | 分块预填充 | **长 prompt / 多模态必开**，避免队头阻塞 |
| `--enable-prefix-caching` | 前缀 KV 复用 | **必开**。命中条件：多次请求共享同一前缀（系统提示、few-shot、相同文档、长会话历史）。收益：System Prompt + 检索文档前缀可省 30–70% prefill |
| `--quantization awq/gptq/fp8` | 权重量化 | 24G 卡跑 14B/32B 的关键。AWQ 精度损失通常 <1%（估） |
| `--kv-cache-dtype fp8` | KV 量化 | 显存再省 50%，长上下文收益大，精度影响小（估 <0.5%） |
| `--tensor-parallel-size` | 张量并行度 | 2 或 4；跨机用 `--pipeline-parallel-size`（吞吐优先） |
| `--enable-eager` | 关闭 CUDA Graph | **不要开**（仅调试用），CUDA Graph 带来 10–20% 提升 |

**Prefix Caching 命中条件与收益（量化说明）**
```
命中率 ≈ (共享前缀 token 数) / (总输入 token 数)
节省的 prefill 时间 ≈ 命中率 × prefill 时长
典型 Agent 场景：System(200) + Tools(800) + History(1200) = 2200 共享前缀
              请求总输入 3500 → 命中率 ≈ 63% → prefill 时间减少约 60%
```

**Speculative Decoding（投机解码）**
- 原理：用小 draft 模型猜 5–10 个 token，大模型一次并行验证，命中率 α 时加速比 ≈ `(1-α) + α × γ`，γ 为验证批长。
- Draft 模型选择：
  - **同系列更小尺寸**（如 Qwen3-32B ← Qwen3-4B；Llama-70B ← Llama-8B）—— 最佳，词表/分词器一致。
  - **EAGLE-2 / Medusa** 头 —— 命中率高 1.5–2×，需要额外训练/下载 head（数百 MB）。
  - **n-gram / Lookahead** —— 零训练成本，对复制粘贴类文本（代码、表格、日志）有效。
- vLLM 支持 `--speculative-config '{"model":"...","num_speculative_tokens":5}'`；SGLang 原生 `speculative_algorithm: "EAGLE3"`。
- 收益（估算）：decode 阶段 1.3–2.0×；**但会占用额外显存**，且在低并发下收益明显、高并发满载时可能反而变慢。

**Continuous Batching（连续批处理）**
- 传统 static batching：等最慢序列跑完才整批换入 → GPU 严重空转。
- 连续批处理：任一序列结束立即换入新序列 → 吞吐可提升 **2–5×**（估）。
- 这是 vLLM/SGLang 的默认行为，也是"选框架比选卡更影响吞吐"的根本原因。

## 6. 训练 / 微调资源表

### 6.1 显存构成

```
训练总显存 ≈ 权重 + 梯度 + 优化器状态 + 激活 + 通信缓冲 + 碎片

【全参微调】
  BF16 权重           = P × 2
  BF16 梯度           = P × 2
  AdamW 优化器状态(m,v) = P × 8   (FP32 master weight 另加 P×4 可选)
  → 小计 ≈ P × 12 ~ 16 bytes
【LoRA (BF16 基座 + BF16 训练)】
  基座权重(冻结)      = P × 2
  LoRA 参数 + 梯度 + 优化器 ≈ (可训练参数量 r×(d_in+d_out)) × 12
  → 对 7B/14B/32B，LoRA 可训练参数常 < 0.5%，优化器开销可忽略
【QLoRA (4bit 基座 + BF16 计算)】
  基座 4bit          = P × 0.5
  + 量化常量开销      ≈ +10%
  + LoRA/优化器       ≈ 可忽略
  → 约为 BF16 全参的 1/25 ~ 1/30
【激活显存】≈ batch × seq_len × hidden × layers × k  （开 gradient checkpointing 后降为 ~1/√ 或按层重算，常数降到 10~20%）
```

### 6.2 微调资源表

| 模型 | 全参微调 (BF16 + AdamW) | LoRA (BF16 基座) | **QLoRA (4bit)** | 推荐卡 | 说明 |
|---|---|---|---|---|---|
| **7B (Qwen3-8B)** | ~120 GB → 2× A100-80G (DDP/FSDP) | ~26 GB → 1× 5090 32G / 1× L20 48G | **~10–12 GB → 1× 4090 24G** | 4090 / L20 | QLoRA 24G 完全可行，`per_device_batch=2~4, seq=2048` |
| **14B (Qwen3-14B)** | ~220 GB → 4× A100-80G | ~46 GB → 1× A100-80G / 1× L20(紧) | **~16–18 GB → 1× 4090 24G** | 4090 / L20 / A100 | 24G 需 QLoRA；48G 可跑 BF16 LoRA |
| **32B (Qwen3-32B)** | ~500 GB → 8× A100-80G (FSDP/ZeRO-3) | ~96 GB → 2× A100-80G | **~24–26 GB → 1× 5090 32G (紧) / 1× L20 48G (舒适)** | L20 48G / A100-80G | 48G 单卡 QLoRA 是最现实的 32B 微调方案 |
| **70B 级** | ~1.2 TB → 8× H100/H200 | ~200 GB → 4× 80G | ~48–56 GB → 2× L40S/1× H100 80G | H100 | 半导体场景通常无需 70B 微调 |

> 说明：上表不含激活与通信缓冲，**实际占用再乘 1.2~1.4**。表中的 32B QLoRA 24GB 是"极限值"，真实配置（`seq_len=2048, bs=1, grad_ckpt=on`）在 24G 卡上会 OOM，请用 32G/48G。

### 6.3 LoRA vs 全参对比

| 维度 | LoRA / QLoRA | 全参微调 |
|---|---|---|
| 显存 | 7B: 26GB(LoRA) / 11GB(QLoRA) vs 120GB | 7B: ~120 GB |
| 卡数（7B） | 1 张消费卡 | 2× A100-80G |
| 效果 | 通用指令/风格/格式对齐：接近全参（估） | 领域知识注入：略优（估 2–5 个百分点） |
| 灾难性遗忘 | 更小（基座冻结） | 风险更高 |
| 产出物 | 几十 MB adapter，可多版本共存 | 全量权重（GB 级），版本管理麻烦 |
| 数据量需求 | 500–5,000 条高质量样本即可见效 | 通常 10,000+ 条 |
| 迭代速度 | **小时级** | 天级 |
| 适用 | ✅ 领域问答格式、术语表、报告风格 | ✅ 机理模型、检测代码、专用能力 |

**推荐**：半导体测试设备公司的场景（内部知识问答、缺陷描述生成、报告撰写）**用 LoRA/QLoRA 即可**，把省下的预算投入 **高质量标注数据**（收益远高于换更大卡）。

### 6.4 显存优化手段

| 手段 | 显存节省 | 代价 | 适用 |
|---|---|---|---|
| **Gradient Checkpointing** | 激活降 60–80% | 慢 20–35% | 必开 |
| **ZeRO-2**（优化器+梯度分片） | 降 ~50–60% 总显存 | 通信增加 | 2–4 卡 |
| **ZeRO-3 / FSDP**（参数+梯度+优化器全分片） | 降 ~75–85% | 通信带宽要求高，需 NVLink | 4–8 卡，32B+ 必用 |
| **序列并行 (SP / Ring Attention)** | 长序列激活与 KV 降 N 倍 | 实现复杂 | 100k+ 长上下文训练 |
| **Paged AdamW / 8-bit Adam** | 优化器状态降 50–75% | 轻微质量损失 | 显存紧张时 |
| **CPU offload (DeepSpeed ZeRO-3 + offload)** | 大幅降显存 | 慢 3–10× | 应急方案 |
| **LoRA / DoRA / rsLoRA** | 降 90%+ | 效果略降 | 首选 |
| **FlashAttention-2** | 激活降 ~30%，长序列加速 1.5–2× | 无 | 必开 |
| **BF16 混合精度 + 梯度累加** | — | — | 必开 |

### 6.5 数据量与时长粗估

```
【数据量】
  LoRA 领域微调： 500 ~ 3,000 条 (问答对 / 指令样本)，每条 200~1,500 token
  典型 1,000 条 × 800 token = 0.8M token

【训练时长估算】（QLoRA, 7B, 单卡 4090, seq=2048, bs=1, grad_accum=8）
  训练吞吐 ≈ 700–1,500 tok/s (4090, 估算)
  总训练 token = 0.8M × 3 epochs = 2.4M token
  训练时长 ≈ 2.4M ÷ 1,000 ≈ 2,400 s ≈ 40 分钟
  → 单次微调 < 1 小时，可以做多轮实验（换数据/换超参）

【全参微调 7B on 2× A100-80G】
  吞吐 ≈ 8,000–15,000 tok/s → 2.4M token ≈ 3–5 分钟/epoch
  但 换卡/换环境/数据准备/评估 的工程时间远大于训练本身
```
**关键结论**：**微调瓶颈是数据准备和评估，不是 GPU**。用 2 张消费卡跑通一个完整 LoRA 流程，往往比直接买 2 张 A100 更值得先做。

### 6.6 微调示例命令（LLaMA-Factory / axolotl）

## 7. 采购 / 选型决策建议

### 7.1 分档推荐方案

#### 🅰 方案 A —— 最低可用（约 20–40 万级）

**配置**：`1× RTX 5090 32GB`（约 2.2 万）+ 配套工作站（主机/电源/散热，约 3–6 万）
**备选**：`2× L20 48GB`（约 8–11 万，但采购/机房门槛高，落入方案 B 区间）

| 维度 | 结论 |
|---|---|
| **能跑什么** | Qwen3-8B / 14B（FP8）、Qwen3-32B（AWQ-INT4，短上下文）、Qwen3-30B-A3B（AWQ-INT4）；bge-m3 / reranker / nomic-embed 同机部署；可做 7B–32B 的 QLoRA 微调 |
| **不能做什么** | 70B+ 模型；DeepSeek-V3；128K 长上下文（KV 装不下）；高并发（>20 路）稳定服务；不能做张量并行（单卡） |
| **可支撑并发** | 8B FP8：约 30–60 路（32K 上下文）；32B AWQ：约 8–20 路（8K–16K 上下文） |
| **团队规模** | 30–80 人内部使用，PoC / 单团队试点 / 边缘节点 |
| **扩展路径** | 加第二张 5090（→ 方案 B 的"工作站集群"）；或改用 2× L20 升级为生产形态 |
| **混合量化取舍** | 主力模型 BF16 不现实，**必须 FP8（若卡支持）或 AWQ-INT4**；Embedding/Reranker 用 INT8 即可；建议 **FP8 KV Cache + Prefix Caching** 补回并发 |
| **额外成本** | 电源需 1200W+、机箱需大尺寸、机箱散热；办公室放置需注意噪音与 575W 发热 |

> **重要提醒**：RTX 5090 在中国大陆的正式供货存在合规与渠道不确定性，采购前须与法务/IT 确认；同时建议同步询价 **L20 / L40S**（数据中心卡，风冷双槽，可上机柜，售后正规）。

#### 🅱 方案 B —— 推荐生产（约 100–200 万级）

**配置**：`4× L20 48GB` 或 `4× L40S 48GB`（单机 4 卡，约 20–34 万卡成本）或 `2× H100 80GB`（约 50–76 万）

| 维度 | 4× L20/L40S 单机 | 2× H100（单机双卡） |
|---|---|---|
| **能跑什么** | Qwen3-32B FP8 单实例（TP=1, 48G 刚好）或 4 个独立实例；30B-A3B FP8；72B AWQ（TP=4） | Qwen3-32B BF16 长上下文；72B FP8（TP=2，2×80G=160G）；MoE 多实例 |
| **并发** | 32B FP8 单实例 30–80 路（32K）；或 4 实例共 120–250 路 | 32B 60–150 路；72B 20–50 路 |
| **单机多卡 vs 双机** | **单机 4 卡优于 2 机 × 2 卡**：NVLink/PCIe 同域通信延迟低；故障域小；运维简单；扩容只需换整机 | H100 SXM 需特定服务器（HGX 风格），单机 2 卡 PCIe 版互联弱，务必确认是否 SXM/NVLink |
| **团队规模** | 200–800 人；或作为 MLOps 平台供多个团队共用 | 200–800 人，含较高 SLA 需求 |
| **扩展路径** | 扩到 2 台 4 卡 → 8 卡；挂对象存储做模型仓库；接 Prometheus 监控 | 加节点做 PP（流水线并行）横向扩展 |
| **混合量化取舍** | 32B/72B 用 FP8 + INT4 双轨（FP8 保精度给重要业务，INT4 保吞吐给批量业务）；Embedding 模型用 INT8 共卡 | 大显存允许 BF16 主模型 + FP8 KV，精度优先 |

> **强烈推荐 4× L20 单机**：48G×4 = 192G 总显存，可同时跑 4 个 FP8 大模型实例（隔离性好，不互相抢 KV 池），或 1 个 72B AWQ + 2 个小模型；TCO 约为 2× H100 的一半，而多实例部署对内部场景反而更实用。

#### 🅲 方案 C —— 旗舰（400 万级+）

**配置**：`8× H200 141GB` 单机（≈300–360 万）或 H100 集群 4–8 节点

| 维度 | 结论 |
|---|---|
| **能跑什么** | **DeepSeek-V3 671B（FP8 权重 671GB → 8×H200 = 1,128GB，余量放 KV + 激活）**；Qwen2.5-VL-72B BF16 多实例；千亿级自研模型训练/微调 |
| **并发** | 32B BF16 多实例 300+ 路；72B 100+ 路；DeepSeek-V3 20–60 路 |
| **团队规模** | 全公司 + 对外服务；或作为多业务共享的推理中台 |
| **扩展路径** | InfiniBand 组网做多机 TP/PP；引入量化路由层（不同模型不同卡池）；建立模型仓库与灰度发布 |
| **混合量化取舍** | 用 FP8 做默认精度、FP4 做低成本副本、INT4 做长上下文降本副本；同一模型多版本共存，按场景路由 |
| **额外要求** | 需液冷/高密机柜（8×700W = 5.6kW/节点）、专业运维、IB 网络、企业级支持合同 |

| 方案 | 优势 | 迁移成本提示 |
|---|---|---|

```

       + 年电费
       + 年机柜与运维分摊
       + 年软件/订阅(可选，如 NVIDIA AI Enterprise)

年电费 = TDP(kW) × 负载率(0.6) × 年运行小时(8000) × 电价(0.8 元/kWh)
        = TDP × 0.6 × 8000 × 0.8 = TDP × 3,840 元/年
```

```
保守值： 1200/1e6 × 2 + 400/1e6 × 8 = 0.0024 + 0.0032 = ¥0.0056 / 请求 (0.56 分)
中等值： 1200/1e6 × 0.5 + 400/1e6 × 1.5 = 0.0006 + 0.0006 = ¥0.0012 / 请求
```
→ 采用保守值做盈亏平衡分析（更稳健）。

**盈亏平衡点计算**
```
以方案 B-1（4× L20）年 TCO = 10.5 万计：
  所需年 API 等价成本 = 105,000 元
  所需年请求数 = 105,000 ÷ 0.0056 = 18,750,000 次/年
  → 日均请求数 = 18,750,000 ÷ 365 ≈ 51,400 次/天
  → 日均 token = 51,400 × 1,600 ≈ 8,200 万 token/天
```
用中等单价再算一次（API 更贵，自建更早回本）：
```
  所需年请求数 = 105,000 ÷ 0.0012 = 87,500,000 次/年 → 日均 24 万次
```

**盈亏平衡表（汇总）**

| 自建配置 | 年 TCO | 盈亏平衡请求数/天 (按保守单价 ¥0.0056/次) | 盈亏平衡 token/天 | 对应人数 (30 次/人/天) |
|---|---|---|---|---|
| 1× 5090 (A) | 3.0 万 | 14,600 | 2,340 万 | 约 490 人 |
| 4× L20 (B-1) | 10.5 万 | 51,400 | 8,220 万 | 约 1,710 人 |
| 4× L40S (B-2) | 15.0 万 | 73,400 | 1.17 亿 | 约 2,450 人 |
| 2× H100 (B-3) | 23.0 万 | 112,500 | 1.80 亿 | 约 3,750 人 |
| 8× H200 (C) | 120 万 | 587,000 | 9.39 亿 | 约 19,600 人 |

**结论（务必向管理层讲清楚）**
1. **以经济性论，200 人规模的内部应用永远不该自建**（年 API 费用仅约 3,000–6,000 元，而自建 TCO 10 万级）。
2. **自建的第一动因是数据合规**：数据不出内网、可离线、可私有微调、可审计、无外网依赖。这在半导体测试设备行业是**刚性要求**，因此 TCO 应视为"合规与可控性的对价"，而不是"省钱"。
3. **自建真正划算的场景**：(a) 规模 ≥1,500 人；(b) 高频自动化（Agent 循环、日志分析、代码助手，每天数万次调用）；(c) 外部 API 不可用/受限（断网、出海、客户现场内网）。
4. **推荐的成本论证方式**：不用"替代 API 省多少钱"，而用 **"单位推理成本"**：
```
方案 B-1 单位成本 = 10.5 万 ÷ (年总 token)
  年总 token ≈ 365 天 × (并发 40 路 × 0.25 有效产出 × 20 tok/s × 8 小时) ≈ 3,650 万 token
  → 单位成本 ≈ ¥2.9 / 百万 token（保守口径，含大量空闲）
  满载时（利用率 80%）≈ ¥1.8 / 百万 token
```
这与商业 API（¥2/¥8 每百万）相比**已具备竞争力**，尤其输出 token 多的场景。

| **TP / EP / DP / PP** | Tensor Parallel（切权重）/ Expert Parallel（切专家）/ Data Parallel（切数据）/ Pipeline Parallel（切层） |

| **Continuous Batching** | 连续批处理，序列结束即换入新请求，vLLM/SGLang 默认 |
| **PagedAttention** | vLLM 的分页 KV 管理，避免传统连续分配造成的碎片 |

| **Chunked Prefill** | 把长 prompt 分块与 decode 混合调度，消除队头阻塞 |
| **Speculative Decoding** | 小模型草稿 + 大模型并行验证，无损加速 decode |
| **AWQ / GPTQ / SGLang / Marlin** | 几种 4-bit 权重量化方案（GPTQ 与 AWQ 为算法，Marlin 为 vLLM 高效 kernel） |

| **Quantization / SmoothQuant / W8A8** | 权重量化 / 激活与权重量化 / INT8 权重+INT8 激活 |
| **MoE / 激活参数** | Mixture of Experts；显存按总参，吞吐按激活参 |
| **QLoRA / LoRA / DoRA** | 4bit 基座 LoRA / 低秩适配 / 带权重的 LoRA |
| **ZeRO-1/2/3, FSDP, DeepSpeed** | 参数/优化器/梯度的分片策略 |
| **Gradient Checkpointing** | 反向传播时重算激活，显存换算力 |
