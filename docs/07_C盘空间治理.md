## 3. 预防机制（重点：让它们以后不再长在 C 盘）

> 删一次只是止血，**不设防就会再长回来**。
> 以下 3 项是永久性的。

### 3.1 环境变量外置（2 个）

#### 为什么选 `E:\PYPROJECT\agent\.cache\` 而不是 `E:\agent-cache\`

| 方案 | 优点 | 缺点 |
|---|---|---|
| `E:\PYPROJECT\agent\.cache\` ✅ | 跟项目走，换机器/重装后路径关系清晰；`.cache` 天然是「缓存」语义；仓库内 `.gitignore` 好管理 | 仓库目录变大（缓存是可再生的，注意别提交） |
| `E:\agent-cache\` | 完全独立于仓库 | 与项目分离，换机/换盘要重新配一次；语义上不与任何项目关联，容易忘 |

**选定 `E:\PYPROJECT\agent\.cache\`**：本机 E 盘是项目与模型的固定盘
（`E:\model` / `E:\PYPROJECT` 都在这），缓存与项目同盘最省心；
且 `.cache` 前缀一眼看出是「可随时删」的再生资源。

#### 已设置的用户级环境变量

| 变量名 | 值 | 作用 |
|---|---|---|
| `PIP_CACHE_DIR` | `E:\PYPROJECT\agent\.cache\pip` | pip 的下载缓存 |
| `HF_HOME` | `E:\PYPROJECT\agent\.cache\huggingface` | HuggingFace 的**全部**缓存（hub / datasets / xet） |

**持久化方式**（写入 `HKCU\Environment`，**新开的**进程才继承）：

```powershell
[Environment]::SetEnvironmentVariable('PIP_CACHE_DIR', 'E:\PYPROJECT\agent\.cache\pip', 'User')
[Environment]::SetEnvironmentVariable('HF_HOME',       'E:\PYPROJECT\agent\.cache\huggingface', 'User')
```

**验证命令与实测输出**：

```powershell
# 1) 确认注册表里确实写进去了
Get-ItemProperty 'HKCU:\Environment' | Select-Object PIP_CACHE_DIR, HF_HOME
#    PIP_CACHE_DIR : E:\PYPROJECT\agent\.cache\pip
#    HF_HOME       : E:\PYPROJECT\agent\.cache\huggingface

# 2) 确认 pip 认了新路径（关键证据）
pip cache dir
#    e:\pyproject\agent\.cache\pip          ← 实测输出

pip cache info
#    Package index page cache location (pip v23.3+): e:\pyproject\agent\.cache\pip\http-v2
#    Package index page cache size: 0 bytes  ← 旧缓存已清空

# 3) 确认 huggingface_hub 认了新路径
python -c "from huggingface_hub.constants import HF_HOME, HF_HUB_CACHE; print(HF_HOME); print(HF_HUB_CACHE)"
#    E:\PYPROJECT\agent\.cache\huggingface
#    E:\PYPROJECT\agent\.cache\huggingface\hub
```

> ⚠️ **关于「必须新开窗口」的准确机制**（实测澄清）：
>
> 用户级环境变量写在 `HKCU\Environment`，**新登录会话**或
> **重启 Explorer** 时，Windows 会把注册表里的值合并进环境块，
> 此后启动的所有进程都会继承。
> 但**当前这个终端的父进程**（Cursor / 旧 PowerShell）是在设置之前
> 启动的，它的 env 块里没有这两个变量 —— **它派生的所有子进程
> 也会继续没有**。所以在本会话里直接跑 `pip cache dir` 仍会看到旧路径。
>
> 实测证据（用注册表值重建环境块后再启动 python，
> 等价于新登录会话的行为）：
>
> ```
> --- HKCU:\Environment 原始值 ---
>   PIP_CACHE_DIR = 'E:\PYPROJECT\agent\.cache\pip'
>   HF_HOME       = 'E:\PYPROJECT\agent\.cache\huggingface'
>
> --- 当前父进程 env ---
>   PIP_CACHE_DIR = ''          ← 旧进程没有继承到
>
> --- 模拟「全新登录会话」：从注册表重建环境块后启动 python ---
>   pip cache dir => e:\pyproject\agent\.cache\pip     ← 外置生效
>
> --- 同法验证 huggingface_hub ---
>   E:\PYPROJECT\agent\.cache\huggingface
>   E:\PYPROJECT\agent\.cache\huggingface\hub
> ```
>
> **结论**：注册表写入是正确且生效的；本会话内看不到是因为
> **父进程太老**，不是配置有问题。**新开一个 PowerShell 窗口
> （或重登一次）即可**。为彻底消除这个坑，项目启动脚本已做
> 注册表回读兜底（见 §3.3）—— **不依赖窗口是否新开**。

> ⚠️ **用户级环境变量只对新进程生效**。已经开着的 PowerShell / CMD
> 窗口里 `$env:PIP_CACHE_DIR` 仍是空的 —— **新开一个窗口**即可。
> 项目启动脚本已做兜底（见 §3.3）。

### 3.2 PyInstaller 打包改为 onedir（根治方案，2026-11-24 已落地）

> ⚠️ **本节已于 2026-11-24 重写**。此前用的是「`--onefile` +
> `--runtime-tmpdir`」的临时方案 —— 它只是把解压目录从 C 盘挪到 E 盘，
> **并没有解决根因**，反而引入了用户可见的严重问题：

> | E 盘被 `_MEI*` 撑掉 7.5 GB | 强杀进程后临时解压目录**不会自动清理** |

> 直接改用 `--onedir`，**不再有任何运行时解压**。

### 3.3 启动脚本继承环境变量（避免旧窗口失效）

**问题**：用户级环境变量**只对新开的进程生效**。如果从「改变量之前
就开着」的 PowerShell 窗口跑 `scripts\restart_api.py`，那么
`os.environ` 里**没有** `PIP_CACHE_DIR` / `HF_HOME`，
此时若直接 `env.setdefault(...)` 就会写入默认值 ——
**反而把「缓存外置」顶掉，缓存又长回 C 盘**。

**实测证据**（从旧窗口启动的 Python 进程）：

```
当前进程 PIP_CACHE_DIR = None
当前进程 HF_HOME       = None
setdefault 后 PIP_CACHE_DIR = SHOULD_NOT_APPEAR   ← 默认值会顶掉用户级设置
注册表用户级 PIP_CACHE_DIR = E:\PYPROJECT\agent\.cache\pip
注册表用户级 HF_HOME       = E:\PYPROJECT\agent\.cache\huggingface
```

#### 改法 1：`scripts\restart_api.py` —— 从注册表回读

新增 `_user_env()` / `_apply_cache_env()` 两个函数：

```python
def _user_env(name: str) -> str:
    """读 Windows **用户级**环境变量（HKCU\\Environment）。"""
    val = os.environ.get(name, "").strip()
    if val:
        return val
    if os.name != "nt":
        return ""
    try:
        import winreg  # type: ignore  # noqa: PLC0415

        with winreg.OpenKey(winreg.HKEY_CURRENT_USER, "Environment") as key:
            raw, _ = winreg.QueryValueEx(key, name)
        return str(raw).strip()
    except (FileNotFoundError, OSError):
        return ""


def _apply_cache_env(env: dict[str, str]) -> None:
    """把缓存外置相关的环境变量注入子进程环境。"""
    for name in ("PIP_CACHE_DIR", "HF_HOME"):
        val = _user_env(name)
        if val:
            env[name] = val
            print(f"[env] {name} = {val}（缓存已外置，不写 C 盘）")
        else:
            print(f"[warn] 未找到 {name}，缓存可能仍落在 C 盘"
                  "（用户级环境变量仅对新进程生效）")
```

调用点（紧跟在 `env.setdefault("HF_HUB_OFFLINE", "1")` 之后）：

```python
# ---- 缓存外置（pip / HuggingFace）→ 强制指向 E 盘 ----
_apply_cache_env(env)
```

> **为什么不改 `setdefault` 的用法**：`env.setdefault` 本身没问题
> （它**不会**覆盖已存在的值）——问题在于**旧进程的 `os.environ` 里
> 本来就没有那个值**。所以真正的修法是「把用户级值补进 `os.environ`」，
> 而不是改 `setdefault` 的语义。

#### 改法 2：`deploy\start_servers.ps1` —— 同样回读注册表

```powershell
# ---------- 缓存外置（pip / HuggingFace）→ 避免 C 盘再次被撑大 ----------
foreach ($_cacheVar in @('PIP_CACHE_DIR', 'HF_HOME')) {
    if (-not $env:$_cacheVar) {
        $_reg = [Environment]::GetEnvironmentVariable($_cacheVar, 'User')
        if ($_reg) {
            Set-Item -Path "Env:$_cacheVar" -Value $_reg
            Write-Host "[env] $_cacheVar = $_reg（从用户级环境变量回读）" -ForegroundColor DarkGray
        } else {
            Write-Host "[warn] 未找到用户级 $_cacheVar，缓存可能仍落在 C 盘" -ForegroundColor Yellow
        }
    } else {
        Write-Host "[env] $_cacheVar = $($env:$_cacheVar)" -ForegroundColor DarkGray
    }
}
```

#### 实测验证

```
=== _user_env 单项回读 ===

  HF_HOME       = E:\PYPROJECT\agent\.cache\huggingface

=== _apply_cache_env 注入结果 ===

[env] HF_HOME       = E:\PYPROJECT\agent\.cache\huggingface（缓存已外置，不写 C 盘）

### 4.3 安全机制

1. **白名单**：脚本**只认三类**目标 ——
   `%TEMP%\_MEI*`、`%LOCALAPPDATA%\pip\Cache`、`~\.cache\huggingface`。
   其它路径一概不进入候选集。
2. **保护名单**（`PROTECTED_PREFIXES`）：以下前缀命中即整体放弃该项 ——
   `C:\ProgramData\miniconda3`、`~\.lmstudio`、`~\.cache\codex-runtimes`、
   `E:\model`、`E:\PYPROJECT`。
3. **逐项占用检查**：删除前检查三个维度 ——
   ① 进程 `ExecutablePath` 以该目录开头（覆盖 onefile 典型场景）；
   ② 进程 `CommandLine` 里出现该目录（覆盖「以该目录为工作目录」）；
   ③ 进程 `WorkingDirectory` 就是该目录。
   **任一命中就跳过并打印占用进程**，绝不强删。
4. **实测差值**：清理前后各读一次 `shutil.disk_usage()`，
   输出**实测释放字节数**，而不是估算。
5. **纯标准库**：不新增任何依赖（`argparse` / `os` / `shutil` / `subprocess` / `pathlib`）。

### 4.4 占用检查的实测验证

造一个**正被进程占用**的 `_MEI` 目录（工作目录设在目录内）：

        路径: C:\Users\admin\AppData\Local\Temp\_MEI0TEST0002
        体积: 4.0 MB
        占用: PID 57100  exe=C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe  cmd=...Set-Location 'C:\Users\admin\AppData\Loc

```

→ `--clean` 时该目录**未被删除**（`Test-Path` 返回 `True`），验证通过。

> ⚠️ **踩过的坑**：第一版只用 `Get-Process` 的 `Path` 字段，
> **漏判**了「工作目录在目录内、但 exe 在别处」的进程。
> 改成 `Win32_Process`（CIM）同时取 `ExecutablePath` + `CommandLine` 后才修好。
> 另一个坑：`subprocess(text=True)` 在 Windows 上用 GBK 解码，
> 遇到非 GBK 字符的进程路径会抛 `UnicodeDecodeError` ——
> 改为**二进制输出 + 手动多编码兜底解码**。

## 5. 后续建议（本次**未执行**）

### 5.1 miniconda 迁到 E 盘（⚠️ 风险高，只写方案）

`C:\ProgramData\miniconda3` 占 **11.66 GB**，是 C 盘第二大户。

**为什么不直接动**（三个理由）：

1. **conda 的环境/包路径与解释器路径是硬绑定的**。`conda` 的
   `prefix` 记录在 `conda-meta\history` 和包记录里，直接复制目录会导致
   `sys.prefix` 错乱、`conda list` 与实际文件对不上、`conda install` 往
   旧路径写。
2. **多个 Python 版本 / 虚拟环境可能都指向这个 base**。
   本项目跑起来依赖 `C:\ProgramData\miniconda3\python.exe`
   （实测 `scripts\restart_api.py` 的 `sys.executable` 就在这里），
   一旦路径变动，所有脚本、计划任务、IDE 解释器配置都要跟着改。
3. **改的过程中如果断电 / 中断，Python 环境可能半残**，
   而 C 盘只有 37 GB 空闲，**没有足够空间做「复制 + 验证 + 回滚」**
   的双份过渡 —— 这正是现在还不能贸然动手的物理原因。

**推荐做法（分阶段，每阶段可回滚）**：

```powershell
# 阶段 1：先备份环境清单（几 MB，随时可重装重建）
conda env export > E:\conda-backup\env-export.yaml
conda list --explicit > E:\conda-backup\explicit.txt

# 阶段 2：装到 E 盘（新装，不动老的）
#   ⚠️ 装完后**不要**立刻删 C 盘那份，先双跑一段时间
conda create -p E:\conda-envs\agent python=3.11 -y
conda activate E:\conda-envs\agent
conda install -r E:\conda-backup\explicit.txt -y   # 按精确版本重装

# 阶段 3：改引用（逐个改，不要一次全改）
#   · 项目脚本里的 python 解释器路径
#   · VSCode / Cursor 的解释器设置
#   · 计划任务、快捷方式的 python.exe 路径
#   · %USERPROFILE%\.condarc 与环境变量 PATH 里的 conda 条目

# 阶段 4：验证通过后（观察 1~2 周），再删 C 盘那份
#   conda clean --all   # 先清 pkg 缓存
#   再手动删除 C:\ProgramData\miniconda3
```

> **一句话**：先在 E 盘**新建**一个环境，用 `explicit.txt` 重装出
> 完全一致的版本，验证项目能跑，再逐个改引用，最后才删 C 盘那份。
> **绝不**直接 `move`/`copy` 现有的 conda 目录。

### 5.2 其它可选优化

| 项 | 收益 | 风险 | 建议 |
|---|---:|---|---|
| `C:\Users\admin\.cache\codex-runtimes`（1.8 GB） | 1.8 GB | 中（codex 依赖） | 等 codex 支持自定义路径再动 |
| `C:\Users\admin\.lmstudio`（3.1 GB） | 3.1 GB | **高**（llama-server 在跑） | 建议把 LM Studio 的模型/后端目录指到 E 盘，但**不要删** |
| Windows 更新缓存 / WinSxS | 数百 MB ~ 数 GB | 中 | 用 `DISM /StartComponentCleanup`，勿手动删 |
| 浏览器 / 微信 / QQ 等应用缓存 | 视情况 | 低 | 各应用自带清理入口，**不要**脚本硬删 |

### 5.3 每月例行检查

建议**每月跑一次**：

```powershell
python scripts\clean_c_drive.py --dry-run
```

- 若输出「预计可释放」为 0 —— 说明一切正常，无需处理；
- 若有数 GB 的可释放量 —— 执行 `python scripts\clean_c_drive.py --clean`；
- 顺便用 `Get-PSDrive C` 看一眼余量，低于 30 GB 就该警惕。
